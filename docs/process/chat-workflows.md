# Выполнение workflow в чате

Эти правила используют входные скиллы Hireminds. Они описывают способ выполнения в текущем
разговоре; порядок команд, gate, условия и пределы циклов берутся из YAML Spec Kit.

## Получить определение

1. Прочитай AGENTS и конституцию. Найди согласованный скоуп и входные данные задачи.
   Исследование идеи не требует разрешения на продуктовую реализацию; само такое
   исследование и его границы должны быть запрошены пользователем.
2. Для workflow, указанного во входном скилле, вызови `specify workflow resolve ID`.
   Это проверка и список активных слоёв, а не запуск. Прочитай базовый
   `.specify/workflows/ID/workflow.yml` и каждый включённый слой из результата resolve.
   Проектные overlays находятся в `.specify/workflows/overlays/ID/`.
3. Примени edits по правилам Spec Kit: к указанным step id добавь, замени или удали шаги.
   Слои с большим числом priority применяются раньше; меньшие числа имеют преимущество.
   При равенстве действует алфавитный порядок ID, последний выигрывает. Resolve показывает
   сильнейшие слои первыми — это не порядок применения. Итог сверяй с его атрибуцией.
   Если источник слоя не найден, YAML невалиден или конструкция непонятна, сообщи конкретную
   проблему и остановись; не подменяй определение запомненным маршрутом из чата или README.
4. Свяжи запрос с `inputs`, используй defaults. `slug`, путь домена и описание относятся
   к текущей задаче, не к прошлому примеру. Не выставляй verdict согласования заранее.
   Кратко сообщи выбранный workflow, слои и точку начала/продолжения. Зафиксируй определение
   в контексте запуска; изменение YAML во время работы не меняет маршрут задним числом.

## Выполнить разрешённые шаги

- **command:** преобразуй имя команды в имя скилла Codex, заменив точки на дефисы:
  `speckit.bug.assess` соответствует `$speckit-bug-assess`. Прочитай его SKILL.md и выполни
  инструкции в этом разговоре с аргументами шага. Проверь prerequisites и фактический
  результат. Блокирующая предпосылка, неприменимый запрос или неразрешённый вопрос
  останавливают продолжение, даже если отдельная программа вернула exit code 0.
  Одного упоминания имени скилла недостаточно.
- **prompt:** выполни задание шага текущим агентом в пределах скоупа.
- **shell:** выполни указанную команду инструментом терминала. Обрабатывай `env` как данные,
  не вставляй пользовательский ввод или вывод модели в исполняемый shell-код.
- **gate:** сначала проведи требуемое review результата. Внутри уже согласованного скоупа
  ведущий агент может продолжить обычный этап по правилам проекта; новый существенный выбор
  обсуждается с владельцем. Различай review агентом и приёмку владельцем. Соблюдай on_reject.
- **условие или цикл:** оцени фактические результаты предыдущих шагов и inputs, соблюдай
  condition и max_iterations из итогового YAML. Не добавляй повторов сверх определения.
- **другой workflow или тип шага:** сначала прочитай его определение и поддерживаемое поведение.
  Если текущая сессия не может выполнить нужное действие или настройку, сообщи ограничение.
  Не имитируй смену модели, параллельное выполнение или доступные только runner возможности.

Результаты capture и выражений храни в контексте выполнения и в материалах, которые
предписывает сам этап. Передавай фактический отчёт проверки следующему шагу. Ошибка команды
останавливает работу, если определение явно не разрешает другое; молчаливое игнорирование
и объявление ошибки успехом недопустимы.

## Артефакты и продолжение

Для функции явно проверь доменную директорию. Если меняется существующий контракт,
сначала прочитай его целиком и сохраняй незатронутые требования; выполняй спецификационный
этап как обновление запрошенного поведения, не сбрасывай файл пустым шаблоном.
Подготовь локальный указатель Spec Kit на выбранный домен. Отсутствующий домен не подменяй
удалённой спекой настройки инструмента или прошлой тестовой фикстурой.

Возобновляя работу, сверяйся с артефактами и подтверждёнными результатами в разговоре;
наличие файла или отмеченной задачи не доказывает прохождение этапа. Не повторяй уже
подтверждённые действия без причины. Этот режим сам не создаёт состояние run YAML-движка.
Не используй `workflow run` или `resume` для запуска другой сессии вместо текущего чата.

После завершения перечисли пройденные шаги, выполненные проверки, оставшиеся проблемы
и фактический статус поставки. Не начинай другой workflow или итерацию автоматически.
Внутренний отчёт сохраняй в проектной системе, не создавай для него продуктовую спеку.

YAML общий для двух режимов, но интерпретация в чате остаётся работой модели.
Программную гарантию исполнения runner этот скилл не предоставляет.
